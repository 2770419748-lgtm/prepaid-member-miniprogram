# 店长无码抵扣 — 后端说明

> **状态：** 已实现（`apps/api` 的 `WalletService.consumeCodeless`，接口 `POST /wallets/:memberId/consume-codeless`）。  
> **日期：** 2026-11-07（Asia/Shanghai）  
> **来由：** 坤总 2026-11-07：「可以给店长开一个无码抵扣的权限，抵扣的不用连接到九讯云的系统，记录在小程序即可」。  
> **和原规则的关系：** 是「消费必须扫会员码」（2026-10-27，见 [pay-code.md](./pay-code.md)）的例外，只给店长和超级管理员。店员仍然只能扫码消费。  
> **硬约束照旧：** 不接微信支付，只记账；余额只经 `WalletService` 改动；不连九讯云。

---

## 1. 什么时候用

顾客没带手机、手机没电、小程序打不开，出示不了会员码时，由**本店店长**（或超级管理员）在工作台按手机号找到会员，直接抵扣。顾客在场能出示会员码时，照旧扫码。

```
工作台首页输入完整手机号            GET /members?phone=...（不变）
会员页「无码抵扣」（只有本店店长、超管看得到）
填九讯云单号（选填，可扫可手输）、商品应付金额、抵扣金额、原因
确认                               POST /wallets/:memberId/consume-codeless
```

## 2. 规则（2026-11-07 默认，坤总可以改）

1. **谁能做：** 超级管理员在任一门店；店长只在自己管的门店（和直接充值、退余额一样）。店员 403：「无码抵扣只有本店店长和超级管理员能做；店员请扫顾客的会员码」。
2. **不要会员码：** 接口不收 `payCode`（带了直接 400），也不会用掉会员当时出示的码。
3. **九讯云单号选填：** 坤总说不用连九讯云，所以没有小票也能抵。**填了单号就和扫码抵扣一样一单一抵**：同一张单全公司只能抵一次（扫码抵过的不能再无码抵，反过来也一样），冲正后放开。
4. **10% 和 1000 元照旧：** 商品应付金额必填，抵扣不能超过它的 10%（向下取整到分），一张单最多 1000 元，也不能超过余额。这是储值抵扣本身的规矩，和扫不扫码无关。
5. **必须写原因：** 去掉首尾空格不能为空，最多 200 字。原因存在流水的 `remark`（会员端不显示），也写进操作记录。工作台给了三个常用原因一点就填：顾客没带手机、手机没电、小程序打不开。
6. **处处标出来：**
   - 流水 `codeless: true`；工作台列表标题「消费 · 无码抵扣」，详情写「办理方式：无码抵扣（店长按手机号办理）」。
   - 操作记录单独一类 `WALLET_CONSUME_CODELESS`「无码抵扣」，payload 带 `codeless: true`、`remark`（原因）、金额、商品金额、前后余额，有单号时带单号。操作人就是办理的店长。
   - 后台流水列表紫色标签「无码抵扣」，「类型」筛选可以选「消费 · 无码抵扣」；导出表格多一列「办理方式」（扫码 / 无码抵扣）。
   - 当日对账每家门店、合计都多「其中无码抵扣 N 笔 X 元」，点一下打开当天的无码抵扣明细；概览「今日消费」下面提一句。
   - 会员自己的明细详情写「办理方式：未出示会员码，门店按手机号办理」，让顾客能发现不是自己办的抵扣。会员看不到操作人和原因。
7. **记错了照常冲正：** 原门店店长或超管冲正，钱退回余额；填过单号的，这张单放开可以重新抵。
8. **会员停用、余额不足照常拒绝；** 同一 `requestId` 重试返回第一次的结果；同一个请求号拿去做扫码消费会被当成另一笔拒绝。

## 3. 接口

| 方法 | 路径 | 谁能用 | 请求 | 返回 |
| --- | --- | --- | --- | --- |
| POST | `/wallets/:memberId/consume-codeless` | 本店店长、超管 | `storeId`, `amountCent`, `productAmountCent`, `remark`（原因，必填）, `requestId`, `orderNo?`, `orderNoTyped?` | 同 M2 记账 |
| GET | `/ledger` | 同 M2 | 另加 `codeless=true\|false` | `true` 只看无码抵扣 |
| GET | `/reconciliation/daily`、`/reconciliation/overview` | 同 P2 | — | 每组数字多 `codelessCount`、`codelessCent`（已算在消费里，不另加减） |

流水（店员视角、会员视角）都多 `codeless` 字段，老流水是 `false`。

| 情况 | 状态码 | 提示 |
| --- | --- | --- |
| 店员、别的门店的店长 | 403 | 无码抵扣只有本店店长和超级管理员能做；店员请扫顾客的会员码 |
| 没写原因、只写空格 | 400 | 请写明为什么没扫会员码，如：顾客没带手机 |
| 没填商品金额、超过 10%、超过 1000 元、单号不对、这张单抵过了 | 同 [order-offset.md](./order-offset.md) | 同扫码抵扣 |

## 4. 数据库

迁移 `20261107100000_codeless_offset`：

- `ledger_entries` 加 `codeless BOOLEAN NOT NULL DEFAULT false`，老数据都是 `false`。
- CHECK `ledger_entries_codeless`：无码抵扣只能是消费，必须有商品应付金额和不为空的原因。
- 改 CHECK `ledger_entries_order_fields`：原来单号、商品金额、手输标记三个同有同无；现在无码抵扣可以只有商品金额没单号，其余（只能是消费、不超过 10%、单号规范写法）不变。扫码消费照旧必须带单号。
- 改 CHECK `ledger_entries_order_offset_cap`：原来「带单号的不超过 1000 元」，改成「带商品金额的不超过 1000 元」，没单号的无码抵扣也封顶。老数据带单号就一定带商品金额，照样满足。
- 部分索引 `ledger_entries_org_id_codeless_idx`，给「只看无码抵扣」用。

所以就算绕过接口直接写库，也写不进没原因、没商品金额、超过 10% 或 1000 元的无码抵扣。

## 5. 前端

- **工作台**（`apps/member-mp/staff/`）：会员页「扫码消费」下面多一行「无码抵扣 · 店长权限」，只有当前门店的店长和超管看得到；记账页 `kind=CODELESS`：顶部黄色提示只在顾客出示不了会员码时用；九讯云订单（选填）；商品应付金额、本次抵扣同扫码；「无码原因（必填）」带三个常用原因；确认框写明「没扫会员码，记在你名下」和原因。
- **会员页**：明细详情多一行「办理方式：未出示会员码，门店按手机号办理」。
- **商家后台**：流水列表、详情抽屉、导出、流水筛选、当日对账、概览、操作记录，见第 2 节第 6 条。后台仍然没有扣款入口。
