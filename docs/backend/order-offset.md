# 扫订单码抵扣 10% — 后端说明

> **状态：** 已实现，手填版（`apps/api` 的 `OrderRedemptionService` 和 `OrderController`，扣款仍在 `WalletService`）。  
> **日期：** 2026-11-05（Asia/Shanghai）  
> **来由：** 坤总 2026-11-05：「试试能不能扫这个条形码能够拉取到订单信息……核销的时候就店员扫码订单 然后自动匹配消费金额 按照10%做抵扣」。评估后坤总选了「先做手填版，接口拿到再升级」。  
> **硬约束：** 不接微信支付，只记账。余额只经 `WalletService` 改动。暂不接任何收银系统接口（2026-10-31 坤总定暂不接 ERP）。

---

## 1. 为什么是「扫单号 + 手填金额」

九讯云销售凭证上方的条码是 Code 128，里面只有订单号（小票印「单号：5982」，条码里是「A5982」），**没有机型和金额**。要自动带出金额，得用九讯云「按单号查订单」的接口，目前没有。

所以现在这样做：条码只用来认出是哪张单、防止同一张单抵两次；商品应付金额由店员照小票填，系统按 10% 封顶。以后拿到九讯云接口，只要在扫到单号后多查一次金额、把输入框改成只读，其余（封顶、一单一抵、冲正放开、对账导出）都不用动。

## 2. 流程

```
会员小程序「会员码」                       POST /members/me/pay-code（不变）
工作台「扫码消费」扫会员码                 POST /pay-codes/scan（不变）
工作台「扫订单码」扫小票上方的条码          GET /orders/check?orderNo=A5982 → 抵过就直接提示，不让往下填
店员填「商品应付金额」                     页面自动算「最多可抵」= 10%，余额不够就抵余额
确认抵扣                                 POST /wallets/:memberId/consume（带 payCode、orderNo、productAmountCent）
                                         → 扣款、用掉会员码、占住这张单，在同一个事务里
店长冲正这笔                              POST /ledger/:id/reversal（不变）→ 同一个事务里放开这张单，可以重新抵
```

条码扫不出来时可以照小票手输单号（只输数字），流水上记 `orderNoTyped: true`，后台标「手输」方便抽查。

## 3. 规则（2026-11-05 默认，坤总可以改）

1. **每笔消费都要带订单号。** 没有订单号的消费接口直接拒绝。2026-11-05 以前的消费没有单号，照样合法。
2. **最多抵商品应付金额的 10%，** 向下取整到分（`floor(商品 × 10 / 100)`）。商品应付金额 = 小票「总计」减优惠（SVIP 直降算优惠），只算能用储值抵的商品，**不用小票上的「实收」**（下单时实收常是 0）。
3. **一张单全公司只能抵一次，** 不分门店、不分会员（一单一卡）。并发时两部手机同时抵同一张单，只有一笔成功。
4. **冲正放开：** 抵错了由店长冲正那笔消费，这张单马上可以重新抵。冲正记录本身带原消费的单号，按单号查得到。
5. **订单号写法：** 去空格、转大写，只认 `A` + 1–10 位数字；去掉开头的 0，存成 `A5982`。扫码只认带 `A` 的（扫到 15 位手机串号、13 位商品条码会提示扫错了）；手输时只输数字也行。
6. **防重复提交照旧：** 同一个 `requestId` 重试返回第一次的结果，不会提示「这张单已经抵扣过了」。同一个请求号换了订单号会被当成另一笔拒绝。

## 4. 接口

| 方法 | 路径 | 谁能用 | 请求 | 返回 |
| --- | --- | --- | --- | --- |
| GET | `/orders/check` | 店员及以上 | `orderNo`（扫到或手输的原文） | `{ orderNo, redeemed, message }`。`orderNo` 是整理后的写法；没抵过 `redeemed` 为 `null`；抵过时 `redeemed` 是 `{ entryId, storeName, amountCent, productAmountCent, createdAt }`，`message` 是给店员看的提示（和提交时被拦下的一样）。只是提示，真正的保证在扣款事务里 |
| POST | `/wallets/:memberId/consume` | 店员及以上 | `storeId`, `amountCent`, `payCode`, `orderNo`, `productAmountCent`, `orderNoTyped?`, `remark?`, `requestId` | 同 M2 |
| GET | `/ledger` | 同 M2 | 另加 `orderNo?`（带不带 A 都行） | 抵这张单的消费和冲掉它的那笔 |

流水（店员视角）多三个字段：`orderNo`（冲正记录带原消费的单号）、`productAmountCent`、`orderNoTyped`。会员视角多 `orderNo`、`productAmountCent`。没有单号的流水三个字段都是 `null`。

报错都是白话，工作台直接显示：

| 情况 | 状态码 | 提示 |
| --- | --- | --- |
| 没带订单号 | 400 | 请先扫九讯云小票上的订单码 |
| 订单号格式不对 | 400 | 订单号不对：请扫九讯云小票上的订单条码，或输入小票上的单号 |
| 没填商品应付金额 / 填了 0 | 400 | 请填商品应付金额 / 商品应付金额要大于 0 |
| 抵扣超过 10% | 400 | 这单最多只能抵 129.90 元（商品金额 1,299.00 元的 10%） |
| 这张单已经抵过（含两笔同时抵） | 409 | 这张单已经抵扣过了：11月5日 14:32 在滨江店抵了 129.90 元。一张单只能抵一次；抵错了请店长先把那笔冲正，再重新抵 |

## 5. 数据库

迁移 `20261105100000_consume_order_no`：

- `ledger_entries` 加 `order_no`、`product_amount_cent`、`order_no_typed`。CHECK 约束 `ledger_entries_order_fields`：三个字段同有同无；有就必须是消费、单号是规范写法、`amount_cent × 10 ≤ product_amount_cent`。所以就算绕过接口，也写不进超过 10% 的抵扣。
- 新表 `order_redemptions`（订单占用）：一笔消费一条，记单号和那笔流水；冲正时填上 `released_at` 和冲正流水。
  - 部分唯一索引 `(org_id, order_no) WHERE released_at IS NULL`：同一家公司同一张单，没放开的只能有一条。这是「一单一抵」的真正保证，并发的第二笔撞索引整笔回滚（会员码、余额都不动）。
  - 触发器：不能删、不能 TRUNCATE；只能放开一次，放开后不能再改；单号、流水、公司、时间不能改。
- 占用和扣款在同一个事务里写，放开和冲正在同一个事务里写。

## 6. 前端

- **工作台**（`apps/member-mp/staff/`）：扫完会员码进入抵扣页，先「扫订单码」（`wx.scanCode` 只扫条码），扫到马上查抵过没有；「条码扫不出来？手输单号」。填商品应付金额后自动填抵扣金额（能抵满就抵满，余额不够就抵余额），店员改小可以，改大会拦下。确认框写明订单、商品金额、抵扣金额、抵扣后余额。流水详情显示订单号和商品应付；冲正提示「冲正后这张九讯云订单可以重新抵扣」。
- **会员页**（`apps/member-mp/pages/`）：会员码扣完显示订单号、商品金额；明细详情显示「订单号」「商品金额 x 元（最多抵 10%）」。
- **商家后台**（`apps/admin-web`）：流水列表加「九讯云订单」列（手输的标「手输」，下面一行商品金额）；详情抽屉、冲正弹窗、操作记录都带单号；流水查询可以按单号查；「导出表格」按当前条件导出 CSV（手机号打码，最多 5000 条），给和九讯云对账用。
